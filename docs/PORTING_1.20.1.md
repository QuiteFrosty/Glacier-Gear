# Porting to 1.20.1 — what differs

Not yet implemented (see the note in the PR/commit this file ships with for why). This is the
scoping reference for doing it next.

1.20.1 predates two Mojang rewrites the current 1.21.4 source relies on:

- **Armor/tool materials**: 1.21.4 uses the `ArmorMaterial`/`ToolMaterial` record types
  (`net.minecraft.world.item.equipment.*`). 1.20.1 uses the older `ArmorMaterial` interface (each
  material is its own enum-like implementation) and the `Tier`/`Tiers` interface for tools. Every
  `GlacierArmorItem`/`Glacier*Item`/`Permafrost*Item` class's material definition needs rewriting
  to that older shape - the mechanic code inside them (Frostbite application, Chilling Touch,
  hurtEnemy/mineBlock overrides) does not change.
- **Armor rendering**: 1.21.4's `assets/glacier_gear/equipment/*.json` + `EquipmentAssets` system
  doesn't exist in 1.20.1. Armor texture wiring reverts to the pre-1.21.2 approach: a single PNG at
  `assets/glacier_gear/textures/models/armor/<name>_layer_1.png` (and `_layer_2.png` for
  leggings), referenced automatically by the vanilla armor renderer via the material's texture
  name - no separate client-extension registration needed for basic texture swapping.
- **Registries**: DeferredRegister/RegistryObject/DeferredItem APIs are present in 1.20.1 NeoForge
  and Forge in a similar shape to 1.21.4, so `init/` classes port with smaller changes than the
  item/armor classes do. Fabric's direct `Registry.register` pattern is unchanged across versions.
- **Biome modifiers**: NeoForge/Forge's `add_features`/`add_spawns` biome modifier JSON schema
  exists in 1.20.1 too, but biome IDs differ (no Frozen Peaks/Grove/Snowy Slopes - those are
  1.18+ terrain, present in 1.20.1's overworld, so they do carry over; double check exact biome
  set generated by 1.20.1 worldgen before reusing the same biome list verbatim).
- **Damage types**: 1.20.1 predates the data-driven `DamageTypes` registry MC introduced in 1.19.4
  and expanded since; `DamageTypes.FREEZE`/`IN_FIRE` resource keys used in
  `GlacierArmorSetBonus` should still resolve the same way, but this is exactly the kind of thing
  that needs a local compile check first.

Recommended approach when picking this up: start from the 1.21.4 `neoforge/` module (closest
lineage - NeoForge's first supported version is 1.20.1, the point it forked from Forge), get it
compiling and loading in a 1.20.1 dev environment, then re-derive `forge/` and `fabric/` from that
working baseline the same way the 1.21.4 ports were derived here.
